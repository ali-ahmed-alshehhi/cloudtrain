# 0014 — Monitoring: one job-events reader, Prometheus and Grafana, matching alarms in CloudWatch

- **Status:** proposed (plan agreed on #109: Ali 18 Nov, Mariam item 3, Maitha item 4; contract #125)
- **Date:** 2026-11-20 (renumbered from 0013 on 22 Nov: #149 took 0013 first)
- **Decided by:** Hilal and Adel (Student 10), with Ali (contracts), Mariam (job events), Maitha (scheduler
  metrics), Hamda and Fatma (CloudWatch, #134; dashboard, decision 0013)

## Context
Every service serves `/metrics`, but nothing collected them, and nobody read the `job-events` queue. The
portal must never touch SQS or hold AWS credentials (its alerts come from `GET /api/v1/jobs/events` through
the gateway, decision 0002). We need a dashboard and alerts on a laptop, and a matching set on AWS, without
an AWS account (decision 0011).

## Decision
1. **`job-events-monitor` (port 8011, not published) is the only reader of `job-events`.** It turns events
   into Prometheus metrics (`cloudtrain_job_*`) and CloudWatch Embedded Metric Format lines. Events arrive
   at least once and in any order (Mariam, #109), so it deduplicates on `event_id` and times each attempt on
   (`job_id`, `data.attempt`). `/health` is 200 only after a recent successful read.
2. **Prometheus `v3.5.5` (9090, not published)** reads every service's `/metrics` every 15 s and evaluates
   5 alert rules (`monitoring/prometheus/alerts.yml`, unit-tested with promtool): service down, 5xx share,
   dead letters, outbox backlog, job events not read.
3. **Grafana `12.4.15` on 3001, published on the laptop only.** One provisioned, read-only dashboard
   ("CloudTrain overview", generated by `monitoring/grafana/build_dashboard.py`). Viewers need no login and
   can only look; the admin password comes from `.env` (`GRAFANA_ADMIN_PASSWORD`, a local placeholder),
   never `admin/admin`.
4. **On AWS, three matching alarms in CloudWatch, on AWS's own metrics** (Terraform
   `infrastructure/modules/monitoring`, Hamda and Fatma, #134). They are the AWS counterparts of three local
   rules, not copies: the conditions differ, because AWS measures the queues and the load balancer, not
   our `/metrics`:

   | Local rule (Prometheus) | Fires when | AWS alarm (CloudWatch) | Alarms when |
   |---|---|---|---|
   | `CloudTrainDeadLetters` | a dead letter was counted in the last 10 min (`increase(job_service_dead_letters_total[10m]) > 0`), at once | `<env>-cloudtrain-dead-letters` | the dead-letter queue holds a visible message (maximum over 1 min > 0, 1 period) |
   | `CloudTrainJobEventsNotRead` | no successful `job-events` read for more than 120 s, for 1 min | `<env>-cloudtrain-job-events-not-read` | the oldest message on `job-events` is older than 300 s, for 2 periods of 60 s |
   | `CloudTrainHighErrorRate` | more than 5% 5xx per service (not `/health`), with some traffic, for 5 min | `<env>-cloudtrain-server-errors` (only once the load balancer exists) | more than 5% 5xx at the load balancer (targets + the load balancer's own), for 5 periods of 60 s |
   | `CloudTrainServiceDown`, `CloudTrainOutboxBacklog` | | none | |

   The CloudWatch **dashboard** is Fatma's Pulumi layer (decision 0013, #149), also on AWS's own metrics
   (queues, GPU worker groups, load balancer, ECS). `monitoring/aws/` holds the hand-off for running the
   monitor on ECS: its IAM policy (only `GetQueueUrl`, `ReceiveMessage` and `DeleteMessage` on
   `job-events`) and a dashboard template for its EMF metrics. **The monitor is not deployed on AWS yet**:
   the `application-services` module (#135) does not start it, so there are no `cloudtrain_job_*` metrics in
   CloudWatch.

## Why
- **One reader per queue** keeps "each event counted once" simple, and keeps SQS and AWS credentials out of
  the browser and the portal.
- **Prometheus and Grafana run in Compose**, so the dashboard works with no AWS account and shows the running
  system live. The CloudWatch side shows the same setup on the emulator, where no live data comes in.
- **EMF instead of `PutMetricData`**: the monitor needs no extra AWS permission to publish metrics.
- **AWS alarms on AWS's own metrics** work even when our services are down or not deployed (the queue age
  rises whether or not the monitor runs). The price is that the two sides are not identical: each threshold
  is tested on its own side (promtool locally; Terraform plan and Checkov for AWS), and the table above says
  how they map.

## Trade-offs
- **3 more containers** (15 in Compose), so `make up` needs a little more memory and time.
- **Not instant.** A rule fires only after its condition has held for its `for:` time, checked every 15 s.
  "Service down" (`up == 0` for 1 min): measured pending after 26–31 s, firing after 83–88 s, cleared
  26–31 s after the restart (`docs/evaluation/test-c-speed-and-alert.md`). "Job events not read": the
  condition becomes true 120 s after the last read, and the alert fires about 1 minute later (the `for: 1m`)
  plus up to one evaluation interval, so about 3 minutes; not measured.
- **Durations and counters live in memory.** A restart of the monitor forgets attempts in flight (their
  wait and run time are lost), and its counters start again from 0; Prometheus treats that as a counter
  reset, so `rate()` and `increase()` stay right. Events are never lost: unread ones wait in SQS.
- **No notifications.** Alerts show in Grafana and Prometheus (and CloudWatch); there is no Alertmanager
  or e-mail. Job alerts for users stay in the portal (decision 0002).
- **`/health` 503 ("not ready yet") is not counted as a server error**, so a slow start does not raise the
  5xx alert; a service that stays down is caught by "service down".
- **Two alarms have no AWS counterpart** (service down, outbox backlog), and the server-errors alarm exists
  only once the load balancer does.
- **On the AWS Emulator** the CloudWatch dashboard and alarms exist but get no live data (decision 0011).
