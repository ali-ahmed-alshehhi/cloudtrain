# Monitoring on AWS: what `infrastructure/modules/monitoring` needs (for Hamda + Fatma)

From Hilal + Adel (Student 10). Proposal and agreement: **#109** (item 2). Everything here is ready to use from
Terraform; nothing in this folder is applied by itself. On the AWS Emulator (decision 0011) these resources are
**created to show the setup is right, but receive no live data** (no machines run); the live dashboard is the
local Grafana.

## 1. Where the numbers come from
| Source | Namespace / metrics | Needs |
|---|---|---|
| `job-events-monitor` log lines in **CloudWatch Embedded Metric Format** (stdout → awslogs) | `CloudTrain`: `JobEvents` (dims `Service`, `EventType`), `QueueWaitSeconds` (`Service`), `RunSeconds` (`Service`, `Result`), `EventLagSeconds` (`Service`) | only the normal ECS log setup (execution role), **no `cloudwatch:PutMetricData`** |
| SQS (built in) | `AWS/SQS`: `ApproximateNumberOfMessagesVisible`, `ApproximateAgeOfOldestMessage` for `training-jobs`, `training-jobs-dlq`, `job-events` | nothing |
| Load balancer (built in) | `AWS/ApplicationELB`: `HTTPCode_Target_5XX_Count`, `RequestCount`, `TargetResponseTime` | the ALB's `arn_suffix` |
| ECS (built in) | `AWS/ECS`: `CPUUtilization`, `MemoryUtilization` | the cluster name |

`Service` is always `job-events-monitor`. The format is checked by the monitor's tests
(`monitoring/job-events-monitor/tests/test_consumer.py::test_emf_lines_are_valid_cloudwatch_records`).

## 2. The `job-events-monitor` service

Done in #135: it is one more service in `infrastructure/modules/application-services` (task role in
`modules/service-roles`, image in `container-registry`, log group from `modules/monitoring`).
- One small ECS Fargate task (0.25 vCPU, 512 MB is plenty), image from `monitoring/job-events-monitor/Dockerfile`
  (build with `--build-context contracts=contracts`), port 8011, **not behind the load balancer**.
- Environment: `JOB_EVENTS_QUEUE=job-events`, `AWS_REGION`, no `SQS_ENDPOINT` (real SQS), optional
  `JOB_EVENTS_WAIT_SECONDS=20`, `JOB_EVENTS_EMF=true`.
- Health check: `GET /health` (200 only after a successful read of the queue in the last 120 s).
- **Task role policy** ([`job-events-monitor-policy.json.tftpl`](job-events-monitor-policy.json.tftpl)): `sqs:GetQueueUrl`,
  `sqs:ReceiveMessage`, `sqs:DeleteMessage` on the `job-events` queue ARN **only**. The queues use SQS-managed
  encryption (`sqs_managed_sse_enabled`), so no KMS permission is needed.
```hcl
resource "aws_iam_role_policy" "job_events_monitor" {
  role   = aws_iam_role.job_events_monitor_task.id
  policy = templatefile("${path.root}/../monitoring/aws/job-events-monitor-policy.json.tftpl", {
    job_events_queue_arn = module.message_queue.job_events_queue_arn
  })
}
```

## 3. Dashboard
[`cloudwatch-dashboard.json.tftpl`](cloudwatch-dashboard.json.tftpl), generated by `build_cloudwatch.py` (10 widgets:
job events, queue wait, training time, messages waiting, oldest message, event delay, load balancer errors and
answer time, container CPU and memory).
```hcl
resource "aws_cloudwatch_dashboard" "cloudtrain" {
  dashboard_name = "cloudtrain"
  dashboard_body = templatefile("${path.root}/../monitoring/aws/cloudwatch-dashboard.json.tftpl", {
    region              = var.region
    training_jobs_queue = "training-jobs"
    training_jobs_dlq   = "training-jobs-dlq"
    job_events_queue    = "job-events"
    alb_arn_suffix      = module.application_services.alb_arn_suffix  # once that module exists
    ecs_cluster_name    = module.application_services.cluster_name
  })
}
```

## 4. Alarms (the same as the local Prometheus rules in `monitoring/prometheus/alerts.yml`)
| Alarm | Metric | Condition | Local twin |
|---|---|---|---|
| `cloudtrain-dead-letters` | `AWS/SQS` `ApproximateNumberOfMessagesVisible`, `QueueName=training-jobs-dlq`, Maximum, 60 s | > 0 for 1 period | `CloudTrainDeadLetters` |
| `cloudtrain-job-events-not-read` | `AWS/SQS` `ApproximateAgeOfOldestMessage`, `QueueName=job-events`, Maximum, 60 s | > 300 s for 2 periods | `CloudTrainJobEventsNotRead` |
| `cloudtrain-server-errors` | metric math `100 * 5xx / requests` on `AWS/ApplicationELB`, 60 s | > 5 for 5 periods, `treat_missing_data = notBreaching` | `CloudTrainHighErrorRate` |
| `cloudtrain-monitor-down` | ECS running task count of `job-events-monitor` (Container Insights) | < 1 for 2 periods | `CloudTrainServiceDown` |

```hcl
resource "aws_cloudwatch_metric_alarm" "dead_letters" {
  alarm_name          = "cloudtrain-dead-letters"
  namespace           = "AWS/SQS"
  metric_name         = "ApproximateNumberOfMessagesVisible"
  dimensions          = { QueueName = "training-jobs-dlq" }
  statistic           = "Maximum"
  period              = 60
  evaluation_periods  = 1
  comparison_operator = "GreaterThanThreshold"
  threshold           = 0
  treat_missing_data  = "notBreaching"
}
```
The other three follow the same shape (the 5xx one uses `metric_query` blocks for the metric math).

## 5. What is not here
No Prometheus or Grafana on AWS (cost and work, #109); the local stack covers the live demo. Notification targets
(SNS topics, e-mail) are out of scope: the portal is the notification service (decision 0002).
